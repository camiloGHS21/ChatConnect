DOCUMENTO DE ESPECIFICACIÓN DE REQUISITOS DE SOFTWARE (SRS)
Plataforma SaaS de Comercio Conversacional por WhatsApp y Panel Web Administrativo (ChatConnect)Estándar IEEE 830 / ISO/IEC/IEEE 29148
1. Introducción
1.1 Propósito del Documento
El presente Documento de Especificación de Requisitos de Software (SRS) define de manera formal, completa y exhaustiva los requisitos funcionales, no funcionales, interfaces externas, arquitectura de capas, modelo de datos relacional y reglas de negocio para la plataforma SaaS de comercio conversacional y automatización de pedidos por WhatsApp con panel web administrativo (ChatConnect). Este documento constituye la fuente única de verdad para los equipos de desarrollo frontend (React.js), backend (Node.js / n8n), arquitectura cloud, ingeniería de datos y aseguramiento de calidad (QA).
1.2 Alcance del Sistema
ChatConnect es una plataforma SaaS multiempresa (multi-tenant) desarrollada por Integraciones y Desarrollo Tecnológicos S.A.S. para comercios, distribuidoras y puntos de venta. El sistema integra de manera unificada dos componentes principales: un motor de atención comercial automatizada vía WhatsApp (Meta Cloud API directa + Inteligencia Artificial multimodal en n8n) y un panel web administrativo (CRM básico en React.js) para el control operativo del negocio. El alcance abarca:
• Atención Comercial y Enrutamiento Inteligente: Canal de WhatsApp 24/7 con soporte para texto, audios (Gemini STT), imágenes de productos (Gemini Vision) y ubicaciones GPS, gestionando hilos en 'ia' y derivación a 'humano'.
• Catálogo Dinámico y Búsqueda en Español: Búsqueda indexada de alta velocidad sobre productos mediante Full-Text Search en español (to_tsvector con índice GIN), categorización (categorias), marcas (marcas) y galerías (producto_imagenes).
• Precios por Escala e Inventario en Tiempo Real: Consulta de precios vigentes por listas de precios corporativas (listas_precios) en COP, rangos por escala de volumen (cantidad_minima y cantidad_maxima) y stock disponible calculado (disponible = existencia - reservado).
• Carrito Conversacional y Pedidos ACID: Liquidación automática de subtotales, descuentos, impuestos y fletes en carritos, formalización de órdenes en pedidos con código unívoco (numero_pedido) y reserva atómica de stock con SELECT FOR UPDATE.
• Panel Web Administrativo (CRM Básico en React.js): Interfaz web para comercios y asesores que permite:
- Gestión de Clientes: Consulta de perfiles, historial de compras, geolocalización y datos de contacto.
- Gestión de Catálogo e Inventarios: Creación y edición de productos, categorías, marcas, imágenes, precios y existencias físicas.
- Tablero de Pedidos en Tiempo Real: Monitoreo y cambio de estados de pedidos (pendiente -> confirmado -> despachado) con trazabilidad en pedido_estados.
- Live Chat y Supervisión de Asesores: Visualización de hilos en conversaciones/mensajes, toma de control en modo 'humano' y reasignación.
• Trazabilidad, Auditoría y Resiliencia: Registro de consumo de tokens y latencias de IA (procesamiento_ia), respaldo de webhooks de Meta (eventos_webhook) y control de excepciones operativas (errores_integracion).

2. Descripción General y Modelo de Operación
2.1 Perspectiva del Producto y Arquitectura de Capas
ChatConnect opera bajo una arquitectura desacoplada estructurada en cinco capas complementarias:
1. Capa de Mensajería y Canales: Recepción y emisión directa vía WhatsApp Business Cloud API (Meta) con endpoints HTTPS seguros y auditoría en eventos_webhook (proveedor = 'meta').
2. Capa de Presentación Web (CRM en React.js): Panel administrativo web interactivo y responsive para comercios y asesores, consumiendo servicios de backend bajo autenticación y filtrado multi-tenant.
3. Capa de Orquestación y Backend (n8n / Node.js): Servidor n8n (Self-Hosted en Docker) y servicios Node.js para normalización de webhooks, flujos de conversación, endpoints transaccionales y lógica de negocio.
4. Capa de Inteligencia Artificial: Modelos multimodales de Gemini para extracción de intenciones, generación de diálogo, procesamiento de audio a texto e interpretación visual de imágenes, auditados en procesamiento_ia.
5. Capa de Persistencia y Transacciones: Motor PostgreSQL 16 (base chatbotDatabase) con extensión pgcrypto, índices GIN, restricciones CHECK, columnas generadas y aislamiento por empresa_id.
2.2 Perfiles de Usuario (Actores del Sistema)

Empresa (Tenant / Admin)
Administrador del comercio que accede al CRM en React.js para configurar canales telefónicos, gestionar el catálogo, listas de precios, inventarios y despachos.
Asesor Humano
Operador de servicio que utiliza el CRM para monitorear conversaciones, asumir hilos de chat (modo = 'humano'), responder dudas complejas y actualizar estados de pedidos.
Administrador de Plataforma
Equipo técnico de Integraciones y Desarrollo Tecnológicos S.A.S. que aprovisiona tenants, monitorea infraestructura VPS (Hostinger), n8n y consumo de tokens.
2.3 Supuestos y Dependencias
• Conectividad y Políticas Meta: Disponibilidad ininterrumpida de Meta Graph API y entrega de webhooks HTTPS válidos con identificadores wamid.
• Servicios Multimodales de IA: Conectividad y tiempos de respuesta estables (< 3.0s) en las APIs de Gemini para texto, audio e imágenes.
• Entorno Transaccional y Web: Infraestructura VPS (Hostinger) con Docker, Nginx SSL, Node.js, n8n y PostgreSQL 16 con pool de conexiones optimizado.

7. Reglas de Negocio
Todo dato operativo debe estar asociado obligatoriamente a un empresa_id para garantizar aislamiento multi-tenant.
Solo los productos activos, con categoría/marca vigente y stock disponible mayor a cero podrán ser ofrecidos al cliente final.
El precio aplicado a un producto debe corresponder a la lista de precios vigente, moneda COP y rango de cantidad definido por cantidad_minima y cantidad_maxima.
El stock disponible se calcula como existencia menos reservado; el sistema no permitirá agregar o confirmar cantidades superiores al disponible.
La confirmación de pedidos debe ejecutarse mediante transacción ACID y bloqueo SELECT FOR UPDATE para evitar sobreventas.
Cada pedido debe contar con un numero_pedido único e inmutable, además de historial de estados en pedido_estados.
Todo webhook o mensaje entrante debe validarse por external_message_id o external_id para asegurar idempotencia y evitar procesamiento duplicado.
Cuando la IA no pueda resolver una intención con confianza suficiente o el cliente solicite asesor, la conversación debe cambiar a modo humano.
Los errores de integración, fallos de workflows y consumos de IA deben registrarse para auditoría, trazabilidad y soporte operativo.
